# Plan: make a crash restore correct, then make its delivery work

Two defects, found tonight, in the order they matter. The user is back on 30+ live sessions and
is relying on this to survive the next crash.

---

## P0 — A crash restore will resume the same conversation in several panes at once

### What happens to the user

On the next crash, some conversations come back **two to four times**. Each copy appends to the
same transcript file and they interleave into nonsense. The user loses the conversation — not the
pane, the actual history.

This is not hypothetical. It happened at 16:40 today:

```
16:40:42 FIRED term=1108cd71… sid=20290103-92ac-4457-a20b-e65ece542333
16:40:42 FIRED term=1e5d387e… sid=20290103-92ac-4457-a20b-e65ece542333
```

Two panes, same conversation, same second. It ran duplicated for ~4 hours; the transcript now has
**571 forked parent chains across 1,655 entries** — two writers, provably interleaved.

**Blast radius right now: 5 of 94 recorded conversations are bound to more than one pane.** One
(`20290103`) is bound to four.

### Why

A conversation moves panes over its life (resumed into a new pane, dragged, reopened). The durable
record (`warp-last/<pane>`) is deliberately **never deleted** — that is what survives a crash that
fires `SessionEnd` on the way down. So every pane a conversation ever lived in keeps a record
pointing at it, and after a crash *all of them* resume it.

The existing dedup is **per-pane** and cannot see this:

```
16:40:37 agent already running in pane — skipped (dedup)     # resume-lib agent_running(pane)
```

It answers "is an agent running in THIS pane", never "is this CONVERSATION already being restored
somewhere else". `restore-plan` and `sess` both have the conversation-level check (`busy_sids()`);
the auto-resume hook — the one that actually runs after a crash — does not.

### Fix

1. **Claim the conversation, not the pane.** Before launching, atomically claim
   `~/.superset-recovery/resuming/<sid>` with `mkdir` (atomic, no lock file to corrupt, no pid to go
   stale). If the claim fails, another pane already has it → log and leave this pane a plain shell.
2. **Expire the claim by mtime**, exactly like the existing start-slot pool: no releaser to spawn,
   nothing to signal, no way to deadlock. A crashed launch frees its own claim.
3. **Also check `busy_sids()`** before launching, so a conversation already open in a pane the
   restore is not touching is never resumed either. This makes the hook use the SAME definition of
   "open" as the other three tools rather than a fourth one.
4. **Prefer the most recent pane.** When several panes claim one conversation, the newest record
   wins and the others stand down — it is where the user last had it.
5. **Stale-record hygiene:** when a conversation is successfully resumed in pane A, drop the
   *other* panes' durable records for that sid. They are known-stale by construction.

Fail-open is preserved: any error in the claim path → launch anyway. A restore that refuses to
restore is worse than a busy machine. The ONE exception is a positive "this conversation is already
open" — that must stop, because the alternative is data loss.

### Verified by

- A synthetic two-pane race on a throwaway sid: both call the claim path, exactly one proceeds.
- Replay of the real double-binding set (5 sids): assert exactly one launch each.
- After a real restore: `count(pid per sid) == 1` for every restored conversation, parsed from a
  `ps` snapshot in Python — never `ps | grep`, which matches its own pattern (that false pass is how
  tonight's "45 of 45" was wrong).

## P1 — The generated restore artifact does not open, and silently drops ~1 in 10

### What happens to the user

`restore-plan` writes a Warp **Launch Configuration**; the palette shows *"No Results Found"*, and
`warp://launch/<path>` opened nothing in either documented form. The mechanism that works — proven
45 times tonight — is a **Tab Config** (`~/.warp/tab_configs/<stem>.toml`, opened by
`warp://tab_config/<stem>`), which is what the user already used before any of this.

### Fix

Emit Tab Configs. Format copied from the user's own `claude_x2.toml` / `claude_worktree.toml`:

```toml
# Generated by pane-resume; safe to replace.
name = "Fix shared Gmail IMAP E2E bottleneck"
color = "blue"

[[panes]]
id = "main"
type = "terminal"
directory = "/Users/maxkrasnykh/Mokka/mokka-workspace"
commands = ["cc all --resume <uuid>"]
```

- **`directory` is a real field** — present in `claude_worktree.toml:6-7` alongside `commands`. The
  earlier `cd <dir> && …` form was not just uglier, it was **broken**: zsh's two-argument `cd`
  fails on a path with a space, `&&` swallows the launch, and the pane silently becomes a plain
  shell. That is why `restore_44` never started. **11 of 115** candidate conversations live under
  `/Users/maxkrasnykh/MK Personal/` and would fail exactly the same way.
- **`type = "terminal"` is load-bearing** — without it Warp may spawn its own billed agent harness
  instead of a shell.
- **Identity-bearing stems**: `restore_<first-8-of-sid>.toml`. A positional `restore_3` means a
  different conversation tomorrow, and the file is a permanent one-click artifact — a stale click
  would reopen a live conversation. Same conversation → same file, rewritten, never accumulating.
- **Escaping via a serializer**, not f-strings. `json.dumps` is a valid TOML basic string for this
  subset; titles are arbitrary user prose and one `"` produces a file Warp rejects.
- **GC our own marked files** at the start of every run, and `--clean` to remove them all. The 45
  written tonight polluted the palette until they were moved out by hand.
- **Backups never into a Warp directory** — `~/.superset-recovery/backups/`.
- **`--open` re-checks liveness before EACH open**, not once at write time: 45 opens × 4s stagger
  is 3+ minutes between the guard and the last launch. Modeled on `restore-in-place`'s
  `still_safe()`, which already solved this.
- `--open` uses `?new_window=true` so a restore lands in its own window instead of appending tabs
  to whatever the user is working in.
- `--launch-config` keeps the old YAML emitter for anyone who has one, smoke-tested, not deleted.

### Explicitly NOT in this change

- **The throttle stays exactly as it is.** An earlier draft proposed making it conditional; that
  rested on a misreading — running agents hold zero slots, and "throttle only when the machine looks
  cold" inverts itself during a cold restore, which is the one scenario it exists for. The knob
  already exists per-machine (`starting-cap` / `starting-settle`).
- `-n/--name` (making Claude Code's own session list match the tab name).
- Recording the agent pid for exact liveness (replacing the 15-minute window).
- The SessionEnd-reason fix (a deliberate quit auto-resumed after a restart).
- Per-terminal lock namespacing.
